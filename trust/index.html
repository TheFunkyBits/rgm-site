Catalog trust

A catalog version identifies adaptation data, not proof of the files delivered to a device. HTTPS and strict validation do not establish artifact authenticity.

Successor catalog delivery

The replacement route is not yet active. After separately authorized cutover, new catalogs are unsigned, versioned HTTPS data with logical paths. The new client validates catalog, recognition rules and Profile semantics, uses confined destinations and activates a complete version-scoped cache atomically. An offline cache is unverified for authenticity.

A successful deployment or HTTP response establishes availability, not the identity of served files. Source version tags do not prove delivered bytes or passing tests. No new catalog content signatures, digest receipts or exact-size identity checks are required.

Optional RGM network, archive, file and workload ceilings are absent, increasing resource-exhaustion risk. Safe path handling and platform constraints remain. Cores are part of the Android-signed app, never executable catalog downloads.
